What the diagrams mean

In the relationship plates, arrows run from referenced parent → referencing child. Labels give the number of children allowed for one parent. These overview plates use boxes for readability; entity sheets use Chen rectangles and attribute ellipses.

The complete relationship ledger is authoritative for both directions. A NOT NULL FK means each child has exactly one parent; a nullable FK permits zero or one. Unless a unique FK restricts it, a parent may have zero to many children.

A foreign key does not require a parent to have children. A department can have no courses; an enrollment can have no grade. Cardinality is not a substitute for capacity or availability checks.

Key legend

PK primary key · FK foreign key · UQ unique constraint · NN required / NOT NULL. Underlined Chen attributes are PKs. Composite UQs are listed separately, never as individually unique columns.

Academic structure

Department → Student: each student has 0..1 department because the FK is nullable. Each faculty member and course must belong to exactly one department.

Course vs Offering: the catalog course is reusable; a course offering fixes the course, semester and section. UNIQUE(course_id, semester_id, section) prevents a duplicate scheduled section.

These are associations, not inheritance: a CourseOffering is not an ISA subtype of Course. It represents a scheduled instance and has its own capacity and identity.

CampusOS / ER & EER atlas

Teaching, registration & assessment

Two M:N relationships: Faculty ↔ Offering is resolved by faculty_assignment; Student ↔ Offering is resolved by enrollment. Their pairwise UNIQUE constraints prevent duplicate links.

Assessment: grade.enrollment_id is mandatory and unique, so each grade has one enrollment and an enrollment has at most one grade. Attendance is unique per enrollment and date.

CampusOS / ER & EER atlas

Library, accounts & operational state

Student ↔ Book: a loan is a historical borrowing event. The same student can borrow the same title repeatedly; there is no UNIQUE(student_id, book_id) constraint.

Accounts: a student account references exactly one student; an admin references none. login_throttle and portal_migration are deliberately unconnected operational tables, not missing relationships.

library_book stores a title and a copies count, not individual physical-copy identities. No fine, reservation or multi-author child table is implemented.

CampusOS · EER field guide · 01 / 06

Read Chen notation before reading the schema

Entity–Relationship modeling describes domain objects, their properties and associations. Enhanced ER (EER) adds concepts such as subtype inheritance. A conceptual diagram explains meaning; a relational schema implements that meaning with tables, keys and constraints. They are related, not interchangeable.

ConceptStandard Chen symbolInterpretation / example
Strong entitySingle rectangleHas a complete identifying key of its own: Student, identified by student_id.
Weak entityDouble rectangleLacks a complete independent key; identified by owner key plus a partial key.
RelationshipSingle diamondAn association between entities, such as Student enrolls in Offering.
Identifying relationshipDouble diamondConnects a classic weak entity to its owner; the weak side participates totally.
Simple / single-valued attributeSingle ovalSimple means not decomposed in this model; single-valued means at most one value per entity. These are different properties.
Composite attributeOval branching to component ovalsName → first_name, last_name. Components carry the stored detail.
Multivalued attributeDouble ovalA set of values for one entity: proposed Student phones, not the actual single phone column.
Stored / derived attributeOrdinary oval / dashed ovaldate_of_birth is stored; age can be calculated from it and an as-of date.
Key / partial keySolid / dashed underlineA key identifies an entity globally; a weak entity’s partial key distinguishes it only within one owner.

Cardinality is not participation

1:1, 1:N and M:N describe maximum association counts. A single connector indicates partial participation; a double connector indicates total participation. Min–max labels such as (0,N) and (1,1) make both bounds explicit. Avoid silently mixing Chen symbols with crow’s-foot endpoints.

Keys need business meaning too

Student’s student_id is the selected surrogate primary key. In the current schema, enrollment_number and email are also NOT NULL and UNIQUE candidate keys. A composite key contains multiple attributes; a composite attribute contains meaningful components. Neither term implies the other.

Scope and evidence: current facts below refer to the Next.js/SQLite build, particularly web/lib/schema.mjs and the exported CampusOS schema. The independent PostgreSQL build has its own DDL and runtime behavior; it is not the database behind the SQLite build. Proposed diagrams are teaching models, not migrations or claims of deployed features.

From ovals to columns · 02 / 06

Student attributes: structure, multiplicity and derivation

Composite name, actual single phone

Conceptually, Student.name comprises first_name and last_name. CampusOS already stores these two columns; there is no need to add a redundant name column. “Simple” is relative to modeling needs: first_name is treated as indivisible here even though human naming conventions can be more complex.

The actual student.phone is one nullable VARCHAR(15) value per student. NULL means no recorded value, not an empty collection. A string with commas is still one column value; it does not implement a properly modeled multivalued phone attribute.

Stored input, derived result

date_of_birth is stored and nullable. Age is not currently stored; the dashed oval illustrates a possible calculation, not a verified existing feature. Compute completed years as of a stated date, accounting for whether that year’s birthday has occurred. Subtracting birth year alone is inaccurate.

Proposed multivalue → child relation

To support several numbers, introduce student_phone(student_id, phone), with composite PK (student_id, phone) and FK student_id → student(student_id). Require both columns; each row holds one number, and the PK prevents duplicate numbers for the same student.

Zero rows represents no recorded phones. Optional metadata such as label or verified_at belongs on the child relation. A “one preferred number” rule needs additional enforcement. If a surrogate phone_id is chosen, retain UNIQUE(student_id, phone).

Migrate existing non-NULL phone values deliberately, adapt forms and queries, then decide whether to remove the old field. Do not keep two competing sources of truth. This child table is proposed only.

Viva distinction: composite asks “what parts?”; multivalued asks “how many values?”; derived asks “computed from what?” A name can be composite and single-valued. An unknown birth date should normally yield unknown age; do not invent zero or store a value that becomes stale each birthday.

Inheritance and design direction · 03 / 06

Specialization ↓ · Generalization ↑

PROPOSED ONLY: CampusOS has separate student and faculty entities with independent primary keys. There is no Person supertype in the current implementation. Matching numeric student_id and faculty_id values do not identify the same human.

Specialization: start broad, discover roles

Start with Person and identify more specific entity types: Student has enrollment_number and admission_year; Faculty has employee_code and designation. Shared names and contact facts could move to Person. Each subtype is a subset of Person and inherits its identity, common attributes and applicable relationships.

The subtype is not a second person. In a shared-key mapping, Student.person_id identifies the same entity as Person.person_id. This is an is-a relationship, unlike Student belongs to Department, which associates different entities.

Generalization: start specific, discover commonality

Start with Student and Faculty, observe genuinely shared identity and properties, then abstract Person. The resulting diagram may match specialization; the difference is the reasoning direction. Similar columns alone do not justify merging records or prove inheritance.

Unification needs identity matching, conflict resolution and deliberate migration of references. A person can have different institutional email addresses for different roles, so deciding which facts are truly shared is part of the design.

Do not confuse inheritance with authentication

The SQLite portal’s admin/student role field governs authorization; it does not establish a Person–Student–Faculty hierarchy. An enrollment associates a student with an offering; it is not a Student subtype. Likewise, Active/Inactive is lifecycle state, not automatically specialization. Use inheritance when shared identity and meaningful subtype-specific rules warrant it—not simply to remove similar-looking column names.

Two independent choices · 04 / 06

Membership constraints and inheritance mapping

Disjointness controls simultaneous subtype membership. Completeness controls whether every supertype entity must be classified. Neither choice follows automatically from the other. All Person examples on this page remain proposed only.

CombinationPermitted membership per PersonPossible policy
Total + disjointExactly one of Student, FacultyRegistry includes only these roles and forbids dual membership.
Total + overlappingAt least one; both allowedEvery registered person has an academic role; student-employees are allowed.
Partial + disjointZero or oneOther people may exist, but these two roles are exclusive.
Partial + overlappingZero, one or bothVisitors may have neither role; dual-role people may have both.

In a common EER specialization-circle convention, d means disjoint and o means overlapping; double/single lines from supertype mean total/partial. ISA triangles are another textbook convention. Label the chosen constraints explicitly rather than assuming a triangle alone specifies them.

Three relational strategies

StrategyMapping and strengthsConstraints / limitations
Supertype + subtype tablesPerson(person_id PK, common facts); Student(person_id PK/FK, student facts); Faculty(person_id PK/FK, faculty facts). Common identity is stored once.Supports all four combinations with appropriate enforcement. Base PK/FK structure alone permits partial, overlapping membership; shared reads need joins.
One combined tablePerson holds common and subtype fields. A NOT NULL discriminator can represent total, disjoint membership.Conditional CHECKs validate relevant fields. Partial membership needs a “neither” representation; overlap needs multiple flags or memberships, not one exclusive role value.
Concrete subtype tables onlyCopy common attributes into Student and Faculty; no Person table. Natural for a total, disjoint hierarchy with independent subtype access.Partial membership has nowhere to go. Overlap risks duplicated shared facts and needs coordinated identity. Cross-subtype queries need UNION and global-key planning.

What a shared-key FK guarantees

Every subtype row has an existing Person; each subtype PK allows at most one row per Person in that table. It does not require a subtype for every Person and does not prohibit the same ID in both subtype tables.

What needs more enforcement

Total membership and cross-table exclusivity need a suitable schema strategy or carefully designed transactional checks/triggers. SQLite does not provide PostgreSQL-style deferred constraint triggers. Validate rules at a safe transaction boundary; naive immediate checks can reject a valid multi-step insertion.

Viva: “A foreign key points from subtype to supertype. It proves the parent exists, not that every parent has a child. Disjointness is another rule entirely.”

Identity, associations and mapping · 05 / 06

Associative does not mean classically weak

Associative entity: a relationship with facts

Enrollment links Student and CourseOffering and records enrollment_date and enrollment_status. Current CampusOS uses enrollment_id as surrogate PK and UNIQUE(student_id, offering_id) to prevent duplicate registration. FacultyAssignment similarly has assignment_id plus UNIQUE(faculty_id, offering_id).

These are associative entities implementing M:N relationships. Their required foreign keys make them dependent on valid participants, but they are not classic Chen weak entities merely because they reference parents. A surrogate key does not remove the need for a business uniqueness rule.

Classic weak entity: owner-relative identity

As a hypothetical example, Dependent might have dependent_name as a partial key within an Employee. Its full relational key is (employee_id, dependent_name). Draw Dependent as a double rectangle, the identifying relationship as a double diamond, and total participation on the weak side.

This example assumes names distinguish dependents within each employee; otherwise choose a better partial key. It is not a current CampusOS table. Existence dependency, mandatory FKs or ON DELETE CASCADE alone do not establish classic weak identification.

Conceptual → relational translation checklist

ER constructRelational ruleConstraint to retain
Strong entity / attributesCreate a relation; select PK; flatten composite attributes into components. Usually compute derived values rather than storing them.Other candidate keys remain UNIQUE + NOT NULL where applicable; domains need types and CHECKs.
Multivalued attributeCreate a child relation containing owner FK and one value per row.Typically PK(owner_key, value); avoid comma lists and repeated phone1/phone2 columns.
Weak entityInclude owner key as FK and part of PK, together with the partial key.Owner reference is mandatory; deletion policy is a separate business decision.
Binary 1:NPut the 1-side PK as FK on the N side; place relationship attributes there when appropriate.NOT NULL enforces mandatory parent per child, not that each parent has children.
Binary 1:1Use FK + UNIQUE, preferably on the totally participating side; merge only when semantics justify it.NOT NULL makes that side mandatory. Mandatory participation of the other side needs more enforcement.
M:N / n-ary relationshipCreate an association relation with participating FKs and relationship attributes.Choose key/UNIQUE from cardinality rules; all FKs are not automatically the only candidate key. Binary decompositions may lose n-ary meaning.

Concrete 1:1 check: grade.enrollment_id is NOT NULL, UNIQUE and an FK. Every Grade belongs to exactly one Enrollment; an Enrollment can have zero or one Grade. The schema does not require every Enrollment to have a Grade. Likewise, nullable student.department_id permits an unassigned student; it does not mean an invalid non-NULL department ID is allowed.

Where is age stored?It is not currently stored. date_of_birth is the stored input; age could be derived for an as-of date. Account for birthdays and unknown dates rather than subtracting years blindly.
Does every attribute have just one classification?No. The dimensions are independent: name can be composite and single-valued; date_of_birth is simple, single-valued and stored. A key is an identification role, not a separate data type.
Specialization versus generalization?Specialization starts with Person and discovers Student/Faculty top-down. Generalization starts with those types and extracts Person bottom-up. Both can yield the same hierarchy; Person is proposed, not implemented here.
Can a person be Student and Faculty?A proposed overlapping hierarchy can represent both with one shared identity. Current tables use independent identities; similar names, emails or coincident ID values do not create an explicit identity link.
Does the shared PK/FK enforce the whole hierarchy?No. It ensures each subtype has a Person and unique membership within that subtype. Disjointness and total completeness require additional enforcement or a different mapping strategy.
Why is Enrollment not a weak entity?It represents an association, carries relationship facts and has its own surrogate PK. Classic weak identification uses an owner key plus a partial key. Required references alone are not that definition.
Why keep UNIQUE when you already have an ID?enrollment_id prevents duplicate IDs, not duplicate student/offering pairs. UNIQUE(student_id, offering_id) protects the business identity. The same principle applies to FacultyAssignment.
Does NOT NULL FK mean total participation everywhere?Only for that referencing side: every child must have a valid parent. It does not require each parent to have a child. Always state the direction of the guarantee.
Is this PostgreSQL running inside Next.js?No. The Next.js build uses SQLite through Node’s node:sqlite. The independent PostgreSQL build has separate DDL and database setup; its locking, typing and trigger mechanisms must not be attributed to SQLite.
Does omitting Person violate normalization?Not automatically. Normalization concerns functional dependencies within relations. A shared Person identity is an EER/domain design choice, not a mandatory normalization step.
