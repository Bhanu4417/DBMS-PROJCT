Notation, keys & interpretation

Entity box
One database table.
PK
Primary key; underlined.
FK
Foreign key to parent table.
UQ*
Part of a composite UNIQUE tuple.
NULL
Column is nullable.
Arrow
Child FK points to parent.
0..1 / 0..N
Optional one / many; check participation table.
ISA
Only the explicit Person role links.
Cards list every column on their diagram page. Relationship paths label the child FK and referenced parent. The full relationship register gives min/max participation on both sides; the card arrows are a visual guide, not a replacement for that register.
A NOT NULL foreign key means each existing child has one parent; it does not mean the parent must have a child. A composite unique pair is not a partial key unless it belongs to a weak entity’s owner-relative key.

Person ISA & partial-key relationship detail

Generalization and specialization in the implementation

campus_person is the common supertype key. person_student(person_id PK/FK, student_id UQ/FK) and person_faculty(person_id PK/FK, faculty_id UQ/FK) are subtype-link relations to existing student/faculty rows. The shared Person is explicitly created by an administrator. There is no inference by matching names or emails.

Specialization describes Person → Student / Faculty (top-down). Generalization describes seeing common identity across Student and Faculty and creating Person (bottom-up). Both describe this same ISA structure.

Weak entity and partial key

person_contact has full primary key (person_id, contact_type, contact_value). Its partial key within the owner is (contact_type, contact_value); the same type/value may occur for different Persons. The owner key is needed to identify the whole weak-entity row.

This is distinct from enrollment and faculty_assignment, which are associative entities with surrogate primary keys plus alternate pair uniqueness—not classic partial-key weak entities.

Admin usage: use the sidebar’s “EER Identity” screen at /eer. Create a Person with no, one or both roles; choose existing student/faculty records to link; add or remove phone/email contacts. Unlinking preserves the source record.
No auto-merge, no new Person login and no change to student portal authorization. Person identity is an optional supplemental model. The separate PostgreSQL/FastAPI build is unaffected.

Admin panel: where names and records come from

Student list: actual SQL query template

SELECT s.*,
       s.first_name || ' ' || s.last_name AS full_name,
       d.department_name,
       (SELECT count(*) FROM enrollment
         WHERE student_id=s.student_id) AS enrollment_count
FROM student s
LEFT JOIN department d USING(department_id);

This template is queries.students in web/lib/queries.mjs. The Students screen uses ResourcePage with endpoint /students. API code applies requested filters, search, sort and pagination after fetching these query results.

Search a student's name directly

SELECT student_id, enrollment_number,
       first_name || ' ' || last_name AS full_name,
       email, status
FROM student
WHERE first_name LIKE '%' || ? || '%'
   OR last_name  LIKE '%' || ? || '%'
ORDER BY last_name, first_name;

This is a useful standalone SQL search example, not the precise implementation of the admin's search (the current API filters its joined result rows in JavaScript).

Faculty names and department

SELECT f.faculty_id, f.employee_code,
       f.first_name || ' ' || f.last_name AS full_name,
       f.email, d.department_name,
       f.designation
FROM faculty f
JOIN department d USING(department_id)
ORDER BY f.last_name, f.first_name;

Enrollment name + course + grade

SELECT st.enrollment_number,
       st.first_name || ' ' || st.last_name AS student_name,
       c.course_code, c.course_name,
       sem.semester_name, sem.academic_year,
       g.marks_obtained, g.max_marks, g.grade_letter
FROM enrollment e
JOIN student st USING(student_id)
JOIN course_offering o USING(offering_id)
JOIN course c USING(course_id)
JOIN semester sem USING(semester_id)
LEFT JOIN grade g USING(enrollment_id)
ORDER BY st.last_name, st.first_name;

Admin SQL examples · reports, EER, insert/update

Current report calculations

-- Students grouped by department
SELECT d.department_code, d.department_name,
       COUNT(s.student_id) AS students
FROM department d LEFT JOIN student s USING(department_id)
GROUP BY d.department_id
ORDER BY d.department_code;

-- Grade percentage (actual grades query calculation)
SELECT g.grade_id, st.first_name || ' ' || st.last_name AS student_name,
       c.course_code,
       ROUND(g.marks_obtained * 100.0 / g.max_marks, 2) AS percentage
FROM grade g JOIN enrollment e USING(enrollment_id)
JOIN student st USING(student_id)
JOIN course_offering o USING(offering_id)
JOIN course c USING(course_id);

Admin Reports screen calls /reports/students, /reports/faculty, or /reports/academic. Report calculations live in web/lib/reports.mjs; not all are a single database SQL statement.

The generic admin endpoint builds CRUD statements from a fixed resource/field allowlist in web/lib/api.mjs; values are bound separately. The browser does not send raw SQL.

How to see real executed templates

Admin → SQL activity polls /dbviewer. It shows redacted SQL templates, duration, route and row counts; it intentionally excludes credentials and does not log parameter values. It is bounded in-memory audit history, not a SQL editor.

These are SQLite examples for the Next.js application. Do not paste SQLite syntax blindly into the separate PostgreSQL build.
